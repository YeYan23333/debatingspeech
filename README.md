## 怎么用

对话里把这三件事说清楚就能开工：

1. 完整辩题，例如「童话是/不是梦」
2. 立场，正方或反方
3. 发言时长，例如 3 分钟

例如：

> 童话是/不是梦，反方，3 分钟

但它不会立刻开始写稿。第一步是一份**全场论证框架**：核心概念怎么定、判断标准是什么、要打哪两三条、每条靠什么撑、每个辩位分别负责哪一块。你看了、改了、点头了，才进下一段。

已经有自己的框架？直接把 `.md`、`.txt`、`.json` 或 `.docx` 丢进来。它会先检查框架内部是否自洽，有不一致的地方会说出来，但不会擅自把你的框架换成它的。

框架定了，默认**只写一辩稿**。一辩稿交付之后会问一句还要不要二辩申论、三辩质询问题、四辩总结、自由辩交锋重点和攻防稿；你不说，它不会自动往下写一整套。

好处是所有稿子共用同一套判断标准和核心论点，不会一辩说 A、四辩说 B。

macOS / Linux 把激活命令换成 `source .venv/bin/activate`，复制命令换成 `cp`。

然后在 `config.yaml` 里填模型和接口地址，在本机 `.env` 里填已有的 API Key。真实API不要写进代码，不要上传到聊天。仓库里只放示例文件，说明见 [API 调用教程](references/api调用教程.md)。

### 三个常用命令

```powershell
# 第一步：出框架，先别写稿
python skills/一辩稿DOCX输出/scripts/debate_workflow.py `
  --stage framework --topic "示例辩题" --side 正方

# 框架确认、现象与学理来源实际核验后：写一辩稿
python skills/一辩稿DOCX输出/scripts/debate_workflow.py `
  --stage first --topic "示例辩题" --side 正方 --duration "3分钟" `
  --framework-file "示例辩题-正方-论证框架.docx" --content-sources-file "已核验来源.json"

# 要攻防稿的时候再加资料表
python skills/一辩稿DOCX输出/scripts/debate_workflow.py `
  --stage attack-defense --topic "示例辩题" --side 正方 `
  --framework-file "示例辩题-正方-论证框架.docx" --content-sources-file "已核验来源.json" --evidence-file "evidence.json"
```

已有框架时，第一步直接加 `--framework-file "我的框架.docx"`，脚本不调模型，把框架转成统一格式的 Word，后面照常往下走。


### 各辩位对应什么

| `--stage` | 写出什么 | 文件名后缀 |
|---|---|---|
| `framework` | 全场论证框架 | `-论证框架.docx` |
| `first` | 一辩立论 | `-一辩稿.docx` |
| `second` | 二辩申论 | `-二辩申论.docx` |
| `third` | 三辩质询问题 | `-三辩质询问题.docx` |
| `fourth` | 四辩总结 | `-四辩总结.docx` |
| `free` | 自由辩交锋重点 | `-自由辩交锋重点.docx` |
| `attack-defense` | 攻防稿（含资料原文表） | `-攻防稿.docx` |

想存到别处用 `--products-dir`，要覆盖同名文件用 `--force`。旧的 `generate_docx_with_model.py` 还能跑，但没有框架门控，新任务建议统一用 `debate_workflow.py`。

## 资料表能做什么，不能做什么

- 普通模型 API 不会自己联网查资料。脚本写出来的引注，除非你真去读过原文，否则都只能算线索。
- 攻防资料表的短引有上限：中文 45 字、英文 25 词，每份来源一条，附可点击链接、用途、适用条件和局限。
- 核不实的材料标「待核验」，缺的类别留空，不编造作者、年份和页码。
- 赛事稿只用来学论证的骨架，不当作数据来源，也不抄里面的独特句式和故事。

核验规则细节见 [证据短引规则](references/evidence-quote-table.md) 和 [证据模板](templates/evidence.example.json)。

## 版本更新公告

### V3.2 ｜ 2026-11-12

**Debatingspeech 华语辩论工作流 V3.2 版本更新公告**

经过迭代打磨，华语辩论写作技能 debatingskills 迎来 V3.0 版本之后的第二个功能版本（V3.2）。

自 V3.1 发布以来，材料与表达的边界已经经由优秀的开源插件补齐，我们解决的是下一个问题：题从哪里切进去，各辩位怎样围绕同一个切口推进，结辩怎样把本场说清楚。本次更新没有改动框架先行的主流程，而是把这三处补上，并把重点场次整理成研究记录。因此本次更新号为：V3.2。

**更新内容**

**框架新增“破题帮助”** 论证框架里必须有一节独立写破题，先于主论点：题面重述成双方真正要作的选择，判断词按“应该”“更”“主要源于”“需要”分别承担举证，定义只负责澄清争议。通常给出两三条有实质差别的候选切入点，每条写清一句话切入点、争在哪里、怎样证明、资料怎样接上；候选切口不是额外主论点，也不靠多列几条凑数。

**全辩位写法** 所有稿件承接框架中已确认的切入点、对象和判准，各辩位按分工分别推进同一套证明，而不是各写一套。优化旧稿时先找“结论比证据多走了哪一步、比较是否同口径、听众能否一次听懂”，再改句子。

第四辩位按次加载专用规则，并新增本场交锋记录入口。

**资料表统一格式** 独立资料表与攻防稿内嵌资料表统一为竖版三列：可用资料摘要、资料来源、可核验链接。按资料类型分组，链接下标注核验说明，表前写元信息，表后附“怎么用”与“风险提示”。格式依据用户提供的参考原件，原件中的辩题、条目和核验结论不进入新任务。

**生成检查与文档对齐** 两个模型入口实际动态加载新指南；框架缺破题节停止导出；导入已有框架保留原文并追加待补说明，不额外调用模型。章节识别只防漏项，不能代替论证审阅。

**使用说明**

1. 仍然先出框架。破题帮助里选定切入点、说清证明链和资料缺口之后，再进入各辩位写稿。
2. 框架缺少破题节点不会导出；导入旧框架不会被改写，只会标出需要补齐的破题内容。
3. 需要资料表时版式按统一三列格式输出；资料仍须核验后填写。
4. 成稿前的内容检查只防漏项，出现缺现象、缺学理或来源对不上时会指出具体缺口，不替代人工判断。
5. 已安装旧版本的用户，在技能目录下执行 `git pull` 指令，即可更新至 V3.2。

### V3.1 ｜ 2026-11-01

**Debatingspeech 华语辩论工作流 V3.1 版本更新公告**

经过迭代打磨，华语辩论写作技能 debatingskills 迎来 V3 版本更新后的首个功能版本（V3.1）。

自 V3.0 发布以来，使用场景已从“把整场怎么打想清楚”继续往前推到“每一句话从哪来”。本次更新没有新增功能，也没有改动框架先行的主流程，而是把论证的原料与表达的边界补上：一方面接入可追溯的语料库，让引用的现象与学理能够回到原件；另一方面引入两个外部 skill，分别负责压制防御性写作与成稿后的中文润色。在此基础上，写稿的底线被进一步收紧。因此本次更新号为：V3.1。

**更新内容**

1. **新增辩论语料库**
   将材料整理入库，每份保留原件、提取文本、SHA-256、来源与实际正文主题。库内提供逐份目录 `references/corpus/catalog.md`、方法研究 `references/corpus/analysis.md` 与按辩题检索入口 `references/corpus/index.json`；附件内部的指令性文字不进入指令层，只作为材料使用。

2. **接入 Humanizer-zh**
   保留上游原文与 MIT 许可，用于成稿后的最后一遍中文表达润色。该环节只调整表达，不改动事实、必要限定、来源编号与最低内容要求；辩论场景下的适用边界见 `references/humanizer-debate.md`，避免润色把论证削平。

3. **接入 anti-defensive-writing**
   针对论文与稿件中常见的自我削弱、提前替对方发言、平铺展示等问题，将其规则落到辩论语境（见 `references/debate-anti-defensive-writing.md`），与 V3.0 的论证集中要求配合使用。

4. **写稿底线进一步收紧**
   每篇稿子的正文必须至少包含一个具体可核验的现象和一条有出处的学理，并说明二者如何支持本方论点。只有名称、空泛概括、名言或文末参考文献不算完成；缺项或来源未确认时，不导出正式成稿。详见 `references/minimum-content.md`。

5. **新增检索与检查脚本**
   `skills/一辩稿DOCX输出/scripts/retrieve_corpus.py` 按辩题检索语料，`skills/一辩稿DOCX输出/scripts/content_requirements.py` 在成稿前做结构化内容检查。检查核对正文与提交的来源记录是否对应，不替代人工事实核验；单纯格式转换工具仍可转换已有文本，不代表完成内容审校。

6. **文档与版本号对齐**
   README 与 SKILL.md 的大标题统一为 V3.1，删去旧版“本地更新、未创建远程 Release”的说明，CHANGELOG 补上 V3.1 小节；安装包内补入更新公告，中文路径按 UTF-8 写入，解压不再乱码。

**使用说明**

1. 给出辩题、立场与发言时长后，流程与 V3.0 一致：先生成全场论证框架，确认后再按辩位写稿。
2. 需要引用材料时，可直接要求从语料库检索；正式引用前仍以原件为准。
3. 成稿会先经过内容检查，出现“缺现象”“缺学理”“来源对不上”时会指出具体缺口，补齐后再次生成。
4. 润色环节在成稿之后进行，如不希望改动表达，可在要求中明确跳过。
5. 成品仍统一保存在系统桌面的 `products` 文件夹，命名格式为「完整辩题 - 立场 - 稿件类型」，同名文件默认不覆盖。
6. 已安装旧版本的用户，在技能目录下执行 `git pull` 指令，即可更新至 V3.1。

### V3.0 ｜ 2026-10-31

**Debatingspeech 华语辩论工作流 V3.0 版本更新公告**

很荣幸，经过各位使用者的反馈与迭代打磨，华语辩论写作技能 debatingskills 迎来第三个大版本的正式更新（V3.0）。

自 v2.5 发布以来，使用场景已从单一的一辩稿撰写逐步扩展到整场备赛。本次更新在保留原有写稿、接口与交付能力的基础上，将生成流程重构并补齐多个辩位的成稿能力，进一步提升备赛流程的完整性与稿件之间的一致性，接下来它将迎来更加连续的思考流程。我们对此次更新非常兴奋，因此本次更新迎来了新的大版本号：V3.0。

**更新内容**

1. **新增统一辩论工作流**
   引入统一入口 `debate_workflow.py`，调整生成流程为：先生成全场论证框架并交由使用者确认，确认后再按需生成对应辩位的稿件。各辩位共用同一套立场、判断标准与核心论点，避免不同稿件之间出现论证偏移。

2. **支持框架生成与导入**
   论证框架既可由技能自动生成，也可由使用者提供文件直接导入。导入时脚本会先检查框架内部是否自洽，指出不一致之处，不会擅自替换使用者原有的框架。

3. **扩展辩位覆盖范围**
   在一辩立论之外，新增二辩申论、三辩质询问题、四辩总结、自由辩交锋重点与攻防稿五类稿件，支持按辩位单独生成。各辩位遵循独立的写作职责。

4. **攻防稿附资料原文表**
   攻防稿文内附可用资料原文表，逐条列明资料用途、可能适用的交锋、原文短引、作者与标题及时间、可点击原文链接与适用局限。

5. **论证进一步收紧**
   围绕最强且切题的主张组织论证，不主动增加无关的举证负担，不写备赛流水账，不平铺展示，并减少机械套路化表达，保持自然叙述。

6. **仅生成明确要求的内容**
   默认只生成一辩稿。一辩稿交付后提示可扩展的稿件类型，未收到明确要求时不自动生成整套稿件。

7. **延用原有交付方式**
   保留多模型 API 接入、Word DOCX 直出桌面“products”文件夹、同名稿件防覆盖，以及旧版论据资料表与兼容脚本。

**使用说明**

1. 在对话中给出完整辩题、立场与发言时长三项信息，技能将先生成全场论证框架，确认后再进入写稿环节。
2. 已有论证框架的，可直接提供 `.md`、`.txt`、`.json` 或 `.docx` 文件，无需重新生成。
3. 一辩稿交付后，按提示回复需要生成的辩位；回复「不需要」即结束，不生成其余稿件。
4. 成品统一保存在系统桌面的 `products` 文件夹内，文件命名格式为「完整辩题 - 立场 - 稿件类型」，同名文件默认不覆盖。
5. 如需自行调用脚本，在项目根目录执行 `--stage framework` 生成框架，确认后执行 `--stage first` 生成一辩稿，其余辩位使用 `second`、`third`、`fourth`、`free`、`attack-defense`。
6. 已安装旧版本的用户，在技能目录下执行 `git pull` 指令，即可更新至 V3.0。
